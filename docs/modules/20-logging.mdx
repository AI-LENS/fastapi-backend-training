## Concept

Python's built-in `logging` module is all you need for most applications. A single `basicConfig` call at startup wires up a consistent format across every logger in your app — including third-party libraries.

```
2026-05-01 12:34:56,789 - INFO - app.main - main - startup: {...}
2026-05-01 12:34:56,812 - INFO - app.services.screening_service - screening_service - seeded sites count=3
2026-05-01 12:34:57,001 - WARNING - app.workers.task_runner - task_runner - Task abc already running
```

Every line carries:

| Field | Comes from |
|---|---|
| `%(asctime)s` | Timestamp of the log call |
| `%(levelname)s` | DEBUG / INFO / WARNING / ERROR / CRITICAL |
| `%(name)s` | Logger name — typically `__name__` |
| `%(module)s` | Source file (without `.py`) |
| `%(message)s` | The formatted log message |

### What to NEVER log

- Passwords, tokens, secrets, API keys
- Full request bodies that may contain PII
- Personally Identifiable Information (PII)

## Walkthrough

No new dependencies — this uses Python's stdlib `logging` only.

### Step 1 — Logging configuration

```python app/core/__init__.py
# empty
```

```python app/core/logging.py
"""Application logging configuration (Module 20)."""
from __future__ import annotations

import logging


def configure_logging() -> None:
    logging.basicConfig(
        level=logging.INFO,
        format="%(asctime)s - %(levelname)s - %(name)s - %(module)s - %(message)s",
        handlers=[
            logging.FileHandler("app.log", encoding="utf-8"),
            # logging.StreamHandler(),  # uncomment to also log to console
        ],
    )
    # Quiet noisy libs
    logging.getLogger("sqlalchemy.engine").setLevel(logging.WARNING)
    logging.getLogger("uvicorn.access").setLevel(logging.WARNING)


def get_logger(name: str | None = None) -> logging.Logger:
    return logging.getLogger(name)
```

`basicConfig` is a no-op if handlers are already attached, so it's safe to call once at module level. The `FileHandler` writes to `app.log` in the working directory (next to `main.py`). Uncommenting `StreamHandler` echoes to the console as well.

### Step 2 — Call from `main.py`

```python app/main.py
from app.core.logging import configure_logging, get_logger

configure_logging()
logger = get_logger(__name__)
```

Call `configure_logging()` **before** importing anything that logs, so the root handler is in place when other modules initialise.

Replace any `logger = logging.getLogger(__name__)` across the codebase with:

```python
from app.core.logging import get_logger
logger = get_logger(__name__)
```

This gives you a single place to change the logging setup later.

### Step 3 — Use it in services

```python app/services/screening_service.py
from app.core.logging import get_logger

logger = get_logger(__name__)


async def submit_screening(uow, *, user, payload):
    logger.info("screening.submit_attempt site_id=%s", payload.site_id)
    async with uow:
        screening = await repo.create(uow.session, **payload.model_dump())
        logger.info("screening.submitted screening_id=%s site_id=%s",
                    screening.id, screening.site_id)
        return screening
```

Use `%s` placeholders — stdlib `logging` defers string formatting until the record is actually emitted, so skipped levels cost nothing.

### Step 4 — Request ID middleware (no change needed)

The `RequestIDMiddleware` from Module 18 stores the request ID in a ContextVar. You can include it in any log message by reading it explicitly:

```python app/middleware/request_id.py
from contextvars import ContextVar
from uuid import uuid4
from starlette.middleware.base import BaseHTTPMiddleware

request_id_var: ContextVar[str | None] = ContextVar("request_id", default=None)


class RequestIDMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request, call_next):
        rid = request.headers.get("x-request-id") or str(uuid4())
        token = request_id_var.set(rid)
        try:
            response = await call_next(request)
            response.headers["X-Request-ID"] = rid
            return response
        finally:
            request_id_var.reset(token)


def get_request_id() -> str | None:
    return request_id_var.get()
```

To include the request ID in a log line:

```python
from app.middleware.request_id import get_request_id

logger.info("domain_error method=%s path=%s code=%s request_id=%s",
            request.method, request.url.path, exc.code, get_request_id())
```

### Step 5 — Log levels reference

| Level | Use for |
|---|---|
| `DEBUG` | Verbose detail; disable in production |
| `INFO` | Normal events — login, screening submitted, worker started |
| `WARNING` | Recoverable problems — duplicate submit, cache miss |
| `ERROR` | Unhandled exceptions |
| `CRITICAL` | Service-down conditions |

### What's new

<AccordionGroup>
  <Accordion title="Why basicConfig and not a custom Handler setup?">
    `basicConfig` is the standard one-liner for single-process apps. It wires the root logger so every `logging.getLogger(...)` call anywhere in the process (including third-party libraries) inherits the handler and format. A custom setup is only needed when you want per-logger handlers or multiple formats.
  </Accordion>
  <Accordion title="Why write to app.log instead of stdout?">
    Writing to a file lets you tail, grep, and rotate logs without touching the process. Uncomment `StreamHandler` in `configure_logging` if you also want console output during development.
  </Accordion>
  <Accordion title="How do I rotate the log file so it doesn't grow forever?">
    Replace `FileHandler` with `RotatingFileHandler` or `TimedRotatingFileHandler` from `logging.handlers`:
    ```python
    from logging.handlers import RotatingFileHandler
    handlers=[
        RotatingFileHandler("app.log", maxBytes=10_000_000, backupCount=5, encoding="utf-8"),
    ]
    ```
    This keeps up to 5 × 10 MB files before overwriting the oldest.
  </Accordion>
  <Accordion title="What happens to the audit logs we built earlier?">
    Audit logs (Module 17c) live in the DB. Application logs (this module) live in `app.log`. Different concerns: audit is for compliance, app logs are for debugging. **Don't conflate them.**
  </Accordion>
</AccordionGroup>

## Quick check

<AccordionGroup>
  <Accordion title="Why use %(name)s and %(module)s — aren't they the same?">
    No. `%(name)s` is the logger name passed to `getLogger` — typically the full dotted module path like `app.services.screening_service`. `%(module)s` is just the filename stem (`screening_service`). Both are useful: name for filtering by subsystem, module for finding the file quickly.
  </Accordion>
  <Accordion title="Can I change the log level at runtime?">
    Yes. Call `logging.getLogger().setLevel(logging.DEBUG)` at any point. In production, expose a management endpoint or read from an env var at startup via `settings.log_level`.
  </Accordion>
  <Accordion title="What log level for what?">
    `DEBUG` — verbose dev info; off in prod. `INFO` — normal events (login, screening submitted). `WARNING` — recoverable problems (cache miss-storm, retry triggered). `ERROR` — unhandled exceptions. `CRITICAL` — service-down events.
  </Accordion>
  <Accordion title="Should I log inside every function?">
    No. Log at the boundary of significant state changes: resource created, status changed, worker started/finished, unhandled exception. Logging every internal helper call creates noise and hurts performance.
  </Accordion>
</AccordionGroup>

## Insight

<Tip>
  **The format is a contract.** Once `app.log` feeds a log shipper (Datadog, ELK, Loki), every field in the format string becomes a column you can filter on. Pick the fields you actually search — timestamp, level, logger name — and keep the message human-readable. You can always add a structured layer later; you can't easily parse an inconsistent format.
</Tip>
