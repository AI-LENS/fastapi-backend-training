## Concept

The whole reason we extracted pure functions (pipeline stages, permission policies) was **to make them trivial to test**. Now we collect on that promise.

### Test pyramid

```
        ┌──────────────┐
        │  E2E         │  ← few, slow, expensive to maintain
        ├──────────────┤
        │ Integration  │  ← some (Module 23)
        ├──────────────┤
        │  Unit        │  ← MANY, fast, focused (this module)
        └──────────────┘
```

Aim for many unit tests at the bottom: pure functions, services with fakes, repos against in-memory DB.

### Fakes vs mocks

| | Fake | Mock |
|---|---|---|
| What | Real implementation, simplified backend | Recorded expectations |
| Library | None — write a class | `unittest.mock` |
| Failure mode | Behaves wrong if you wrote a bad fake | Tests pass even when production code is broken (over-mocked) |
| **Use when** | **You can write a small real impl** | **Last resort** |

Default to fakes. They're more code, but tests are more meaningful.

```python tests/unit/test_pipeline_stages.py
"""Pipeline stages are pure functions. Test them with plain dataclasses.

Prerequisites: Module 14 introduced six stage functions in
`app/pipelines/eligibility/stages.py`:
    check_age, check_diagnosis, check_medications,
    check_pregnancy, check_liver_disease, check_other_trial
If you used different names, rename them now (or adjust the import below).

The `_s` factory uses the exclusion fields (`is_pregnant`, `has_liver_disease`,
`in_other_trial`) declared on `ScreeningCreate` in Module 02. The Screening
**model** doesn't store them yet — that's fine for these unit tests since they
operate on plain `SimpleNamespace`s. When you wire stages into the real model
(later in this module) you'll want the corresponding columns; add them then.
"""
from types import SimpleNamespace

import pytest

from app.pipelines.eligibility.stages import (
    check_age, check_diagnosis, check_medications,
    check_pregnancy, check_liver_disease, check_other_trial,
)


def _s(**fields):
    """Tiny ad-hoc factory for stage tests."""
    defaults = {
        "age": 40, "sex": "F", "diagnosis": "Type 2 Diabetes",
        "medications": ["metformin"],
        "is_pregnant": False, "has_liver_disease": False, "in_other_trial": False,
    }
    return SimpleNamespace(**{**defaults, **fields})


@pytest.mark.parametrize("age,passed", [
    (17, False), (18, True), (40, True), (75, True), (76, False),
])
def test_check_age(age, passed):
    result = check_age(_s(age=age))
    assert result.passed is passed


@pytest.mark.parametrize("diagnosis,passed", [
    ("Type 2 Diabetes", True),
    ("Type 1 Diabetes", False),
    ("Hypertension", False),
])
def test_check_diagnosis(diagnosis, passed):
    assert check_diagnosis(_s(diagnosis=diagnosis)).passed is passed


def test_check_medications_empty_fails():
    assert check_medications(_s(medications=[])).passed is False


def test_check_medications_one_passes():
    assert check_medications(_s(medications=["metformin"])).passed is True


def test_check_pregnancy_excludes_pregnant():
    assert check_pregnancy(_s(is_pregnant=True)).passed is False


def test_check_liver_disease_excludes():
    assert check_liver_disease(_s(has_liver_disease=True)).passed is False


def test_check_other_trial_excludes():
    assert check_other_trial(_s(in_other_trial=True)).passed is False
```

### Step 4 — Test permission policies (also pure)

```python tests/unit/test_permissions.py
from types import SimpleNamespace

from app.services.permission_service import (
    _can_access_screening, _can_modify_screening,
)


def _user(**fields):
    defaults = {"id": "u1", "role": "coordinator", "site_id": "SITE-001"}
    return SimpleNamespace(**{**defaults, **fields})


def _screening(site_id="SITE-001"):
    return SimpleNamespace(id="s1", site_id=site_id)


def test_sponsor_sees_all_sites():
    assert _can_access_screening(_user(role="sponsor", site_id=None), _screening("SITE-002"))


def test_coordinator_sees_own_site():
    assert _can_access_screening(_user(site_id="SITE-001"), _screening("SITE-001"))


def test_coordinator_blocked_from_other_site():
    assert not _can_access_screening(_user(site_id="SITE-001"), _screening("SITE-002"))


def test_sponsor_cannot_modify_per_policy():
    """Sponsors are oversight; modification is coordinator-only."""
    assert not _can_modify_screening(_user(role="sponsor", site_id=None), _screening())


def test_coordinator_modifies_own_site():
    assert _can_modify_screening(_user(site_id="SITE-001"), _screening("SITE-001"))


def test_coordinator_cannot_modify_other_site():
    assert not _can_modify_screening(_user(site_id="SITE-001"), _screening("SITE-002"))
```

### Step 5 — Test the orchestrator with composed stages

```python tests/unit/test_pipeline_orchestrator.py
"""Test the orchestrator with composed real stages."""
from types import SimpleNamespace

import pytest

from app.pipelines.eligibility import run_pipeline


def _eligible_screening():
    return SimpleNamespace(
        age=40, sex="F", diagnosis="Type 2 Diabetes",
        medications=["metformin"],
        is_pregnant=False, has_liver_disease=False, in_other_trial=False,
    )


@pytest.mark.asyncio
async def test_eligible_screening_passes_all_stages():
    outcome = await run_pipeline(_eligible_screening())
    assert outcome.eligible is True
    assert outcome.failed_criteria == []
    assert all(r.passed for r in outcome.stage_results)


@pytest.mark.asyncio
async def test_pregnant_screening_fails():
    s = _eligible_screening()
    s.is_pregnant = True
    outcome = await run_pipeline(s)
    assert outcome.eligible is False
    assert "pregnancy" in outcome.failed_criteria


@pytest.mark.asyncio
async def test_multiple_failures_all_listed():
    s = SimpleNamespace(
        age=10, sex="F", diagnosis="Hypertension", medications=[],
        is_pregnant=True, has_liver_disease=False, in_other_trial=False,
    )
    outcome = await run_pipeline(s)
    assert outcome.eligible is False
    # Failures: age, diagnosis, medications, pregnancy
    assert set(outcome.failed_criteria) >= {"age", "diagnosis", "medications", "pregnancy"}
```

### Step 6 — Test the service with a fake repo

```python tests/unit/test_screening_service_fake.py
"""Demonstrates fake-based service tests. Real DB not needed."""
from types import SimpleNamespace
from uuid import UUID, uuid4

import pytest


class FakeScreeningRepo:
    """Drop-in replacement for `screening_repository`."""

    def __init__(self):
        self.store: dict[UUID, SimpleNamespace] = {}

    async def get_by_id(self, db, screening_id):
        return self.store.get(screening_id)

    async def mark_enrolled(self, db, screening, *, subject_id):
        screening.status = "enrolled"
        screening.subject_id = subject_id
        return screening


# We're going to test the *core decision logic* of enroll_screening.
# Rather than instrumenting the real service for fake injection, we
# extract the policy into a small private function. (See exercise.)


@pytest.mark.asyncio
async def test_enrolling_eligible_sets_subject_id():
    """Stand-in for the real test once the service supports DI of repo."""
    repo = FakeScreeningRepo()
    sid = uuid4()
    repo.store[sid] = SimpleNamespace(
        id=sid, status="eligible", eligibility_result="eligible",
        site_id="SITE-001", subject_id=None,
    )

    # Pretend we're calling the service:
    screening = await repo.get_by_id(None, sid)
    assert screening.eligibility_result == "eligible"
    enrolled = await repo.mark_enrolled(None, screening, subject_id="S-ABC123")
    assert enrolled.subject_id == "S-ABC123"
    assert enrolled.status == "enrolled"
```

### What's new

<AccordionGroup>
  <Accordion title="`@pytest.mark.parametrize`">
    Run the same test with multiple inputs. Cleaner than 10 nearly-identical test functions.
  </Accordion>
  <Accordion title="`@pytest.mark.asyncio`">
    Marks async tests so pytest-asyncio runs them in an event loop. With `asyncio_mode = "auto"` in pyproject.toml, you can omit the marker.
  </Accordion>
  <Accordion title="Why `SimpleNamespace` and not the real models?">
    Speed and simplicity. The pipeline stage only reads attributes; it doesn't care if the source is an ORM object, a dict-wrapper, or a `SimpleNamespace`. No DB, no migrations, no engine — tests run in milliseconds.
  </Accordion>
  <Accordion title="`from app.services.permission_service import _can_access_screening` — testing private?">
    Yes, deliberately. The pure functions are *private to the module* but their *behavior* is the most important thing to lock down with tests. The "module is the unit" — internal vs public is a code-organization concern, not a testability one.
  </Accordion>
</AccordionGroup>

## Quick check

<AccordionGroup>
  <Accordion title="What's a good coverage target?">
    Services: 90%+. Pipelines: 100% (it's all pure functions). Repos: 70-80% (covered better at integration level). Routes: 50% — most route logic is integration-tested. Don't chase 100% — the last 5% is rarely worth the effort.
  </Accordion>
  <Accordion title="When would I use a mock instead of a fake?">
    Genuinely external systems with weird interfaces (a finicky third-party API, an SMTP client). Even then, prefer a fake if you can write one cheaply. Mocks tend to lock in implementation details.
  </Accordion>
  <Accordion title="Should I test that exceptions are raised?">
    Yes — `with pytest.raises(SomeException): ...`. It's part of the contract.
  </Accordion>
  <Accordion title="What about flaky tests?">
    Don't tolerate them. A flaky test is worse than no test. Investigate, fix the underlying race, or quarantine until you can.
  </Accordion>
</AccordionGroup>

## Insight

<Tip>
  **Pure functions are tested for a reason: they're testable.** When a colleague says "I can't write tests for this code", what they mean is "the architecture didn't make it possible". Modules 14 (pipelines), 17b (permissions), and 18b (permission service) all paid the architectural cost of purity precisely so this module could be 30 lines of trivial tests instead of a multi-hour test-fixture nightmare.
