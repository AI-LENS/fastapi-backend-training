## Concept

Module 13's worker just runs a coroutine. That's fine for happy paths. Production workers need to handle:

<CardGroup cols={3}>
  <Card title="Transient failures" icon="rocket">
    Network blips, locked rows. Retry with backoff.
  </Card>
  <Card title="Permanent failures" icon="ban">
    Bad data, exhausted retries. Route to a DLQ for human review.
  </Card>
  <Card title="Idempotency" icon="link">
    Re-runs must not double-process. Workers WILL run twice — design for it.
  </Card>
</CardGroup>

| Property | Why critical |
|---|---|
| **Retries** | Transient errors (network, locks) self-heal in seconds. Don't bother humans. |
| **Exponential backoff + jitter** | "Retry every 1s" causes thundering herds. `1s, 2s, 4s, 8s + random jitter` smooths load. |
| **Max retries** | After N attempts, declare permanent failure. Don't retry forever. |
| **Timeouts** | A stuck job must not hold a worker slot indefinitely. Bound every retry. |
| **DLQ (dead-letter queue)** | Permanent failures go to a "needs human" pile, not just `/dev/null`. |
| **Idempotency** | The job ran, but the response was lost — should it run again? Yes. Should it create two enrollments? No. |
| **Concurrency limits** | If 1000 screenings arrive at once, you can't run 1000 workers simultaneously. Cap it. |
| **Graceful cancellation** | When the server shuts down, in-flight jobs need to stop cleanly, not corrupt state. |

## Walkthrough

We'll build a `JobPolicy` wrapper that adds retry/timeout/DLQ around any worker coroutine, plus a small `JobRecord` table to track state across retries.

### Step 1 — Add a job-record table

This survives process restarts (the in-memory `BackgroundTaskRunner` doesn't):

```python app/models/job_record.py
"""A persistent record of every background job — its state, attempts, last error."""
from datetime import datetime
from uuid import UUID, uuid4

from sqlalchemy import DateTime, Integer, JSON, String
from sqlalchemy.orm import Mapped, mapped_column

from app.models.base import Base, TimestampMixin


class JobRecord(Base, TimestampMixin):
    __tablename__ = "job_records"

    id: Mapped[UUID] = mapped_column(primary_key=True, default=uuid4)
    job_type: Mapped[str] = mapped_column(String(50), nullable=False, index=True)
    target_id: Mapped[str] = mapped_column(String(100), nullable=False, index=True)
    idempotency_key: Mapped[str] = mapped_column(String(100), nullable=False, unique=True)

    status: Mapped[str] = mapped_column(
        String(20), nullable=False, default="queued", index=True
    )  # queued | running | succeeded | failed | dead_letter | cancelled

    attempts: Mapped[int] = mapped_column(Integer, default=0, nullable=False)
    max_attempts: Mapped[int] = mapped_column(Integer, default=3, nullable=False)
    last_error: Mapped[str | None] = mapped_column(String(2000), nullable=True)
    last_error_at: Mapped[datetime | None] = mapped_column(DateTime(timezone=True))
    next_retry_at: Mapped[datetime | None] = mapped_column(DateTime(timezone=True))
    payload: Mapped[dict] = mapped_column(JSON, default=dict)
```

Generate the migration: `alembic revision --autogenerate -m "add job_records" && alembic upgrade head`.

### Step 2 — Repository for jobs

```python app/repositories/job_record_repository.py
from datetime import datetime
from uuid import UUID

from sqlalchemy import select
from sqlalchemy.ext.asyncio import AsyncSession

from app.models.job_record import JobRecord


async def get_or_create(db, *, idempotency_key: str, **fields) -> tuple[JobRecord, bool]:
    """Idempotent: if a record exists for this key, return it; otherwise create."""
    result = await db.execute(select(JobRecord).where(JobRecord.idempotency_key == idempotency_key))
    existing = result.scalars().first()
    if existing:
        return existing, False
    record = JobRecord(idempotency_key=idempotency_key, **fields)
    db.add(record)
    await db.flush()
    return record, True


async def mark_running(db, record: JobRecord) -> None:
    record.status = "running"
    record.attempts += 1
    await db.flush()


async def mark_succeeded(db, record: JobRecord) -> None:
    record.status = "succeeded"
    record.last_error = None
    await db.flush()


async def mark_retrying(db, record: JobRecord, *, error: str, next_retry_at: datetime) -> None:
    record.status = "queued"
    record.last_error = error
    record.last_error_at = datetime.utcnow()
    record.next_retry_at = next_retry_at
    await db.flush()


async def mark_dead_letter(db, record: JobRecord, *, error: str) -> None:
    record.status = "dead_letter"
    record.last_error = error
    record.last_error_at = datetime.utcnow()
    await db.flush()


async def get_by_id(db, job_id: UUID) -> JobRecord | None:
    return await db.get(JobRecord, job_id)
```

### Step 3 — A retry policy

```python app/workers/policy.py
"""Retry policy with exponential backoff + jitter."""
from __future__ import annotations

import asyncio
import logging
import random
from dataclasses import dataclass
from datetime import datetime, timedelta, timezone
from typing import Awaitable, Callable
from uuid import UUID

from app.database import async_session
from app.repositories import job_record_repository as job_repo

logger = logging.getLogger(__name__)


@dataclass
class RetryPolicy:
    max_attempts: int = 3
    base_delay_s: float = 1.0
    max_delay_s: float = 30.0
    jitter_pct: float = 0.20  # ±20%
    timeout_s: float = 60.0   # per-attempt cap


class PermanentError(Exception):
    """Signal that retrying won't help. Goes straight to DLQ."""


def _backoff_delay(attempts: int, policy: RetryPolicy) -> float:
    """Exponential: 1s, 2s, 4s, 8s, ... capped, with jitter."""
    base = min(policy.base_delay_s * (2 ** (attempts - 1)), policy.max_delay_s)
    jitter = base * policy.jitter_pct * (random.random() * 2 - 1)
    return max(0.1, base + jitter)


async def run_with_policy(
    job_id: UUID,
    work: Callable[[], Awaitable[None]],
    policy: RetryPolicy,
) -> None:
    """Run `work` with retries and timeout. Updates job_record on each attempt."""

    while True:
        async with async_session() as db:
            record = await job_repo.get_by_id(db, job_id)
            if record is None:
                logger.error("Job %s vanished from DB; aborting", job_id)
                return
            if record.status in {"succeeded", "dead_letter", "cancelled"}:
                return  # already done — idempotent return
            await job_repo.mark_running(db, record)
            await db.commit()

        try:
            await asyncio.wait_for(work(), timeout=policy.timeout_s)

        except asyncio.CancelledError:
            logger.info("Job %s cancelled", job_id)
            raise

        except PermanentError as exc:
            async with async_session() as db:
                record = await job_repo.get_by_id(db, job_id)
                await job_repo.mark_dead_letter(db, record, error=str(exc))
                await db.commit()
            logger.error("Job %s → DLQ (permanent): %s", job_id, exc)
            return

        except (asyncio.TimeoutError, Exception) as exc:
            async with async_session() as db:
                record = await job_repo.get_by_id(db, job_id)
                if record.attempts >= policy.max_attempts:
                    await job_repo.mark_dead_letter(db, record, error=str(exc))
                    await db.commit()
                    logger.error(
                        "Job %s → DLQ (exhausted after %d attempts): %s",
                        job_id, record.attempts, exc,
                    )
                    return
                delay = _backoff_delay(record.attempts, policy)
                next_at = datetime.now(timezone.utc) + timedelta(seconds=delay)
                await job_repo.mark_retrying(db, record, error=str(exc), next_retry_at=next_at)
                await db.commit()
                logger.warning(
                    "Job %s attempt %d failed: %s — retrying in %.2fs",
                    job_id, record.attempts, exc, delay,
                )
            await asyncio.sleep(delay)
            continue

        else:
            async with async_session() as db:
                record = await job_repo.get_by_id(db, job_id)
                await job_repo.mark_succeeded(db, record)
                await db.commit()
            logger.info("Job %s succeeded after %d attempt(s)", job_id, record.attempts)
            return
```

### Step 4 — Concurrency limit

A single semaphore caps how many of these can run simultaneously:

```python app/workers/task_runner.py
import asyncio


class BackgroundTaskRunner:
    def __init__(self, executor, *, max_concurrency: int = 10):
        self._executor = executor
        self._tasks: dict[UUID, asyncio.Task] = {}
        self._semaphore = asyncio.Semaphore(max_concurrency)

    def submit(self, key: UUID, coro_factory) -> None:
        if key in self._tasks and not self._tasks[key].done():
            return

        async def runner():
            async with self._semaphore:           # ← cap concurrency here
                await coro_factory()

        self._tasks[key] = asyncio.create_task(runner())
```

### Step 5 — Wire it into the screening pipeline

```python app/services/screening_service.py
import json
from app.workers.policy import RetryPolicy, run_with_policy
from app.repositories import job_record_repository as job_repo


async def submit_screening(uow, runner, progress, payload):
    async with uow:
        site = await site_repository.get_by_id(uow.session, payload.site_id)
        if site is None or not site.active:
            raise InvalidSite(f"Site {payload.site_id} unknown or inactive")
        screening = await repo.create(uow.session, **payload.model_dump())

        # Create the durable job record (idempotency key derived from screening.id)
        job_record, _ = await job_repo.get_or_create(
            uow.session,
            idempotency_key=f"eligibility:{screening.id}",
            job_type="eligibility_pipeline",
            target_id=str(screening.id),
            max_attempts=3,
            payload={"screening_id": str(screening.id)},
        )
        job_id = job_record.id

        screening_id = screening.id

        def _make_work(target_id, progress):
            """Build the awaitable that `run_with_policy` will execute."""
            async def _work():
                async with async_session() as db:
                    target = await get_screening(db, target_id)
                    await repo.update_status(db, target, status="reviewing")
                    # ... pipeline runs here, reporting via `progress` ...
            return _work

        uow.publish_after_commit(
            run_with_policy,
            args=(job_id, _make_work(screening_id, progress), RetryPolicy()),
        )

        return screening
```

(The exact wiring varies by codebase; the principle: store `JobRecord` in the same transaction as the work intent, then schedule the actual run after commit.)

### What's new

<AccordionGroup>
  <Accordion title="Why does the JobRecord live in the DB?">
    Survives process restarts. If the API server crashes mid-job, on next startup a sweep can find `status='running'` records older than X minutes and either resume (idempotent re-run) or DLQ them. Pure in-memory state can't do this.
  </Accordion>
  <Accordion title="`idempotency_key=f'eligibility:{screening.id}'`">
    Stable, derived key. Two attempts to schedule the same eligibility job for the same screening will hit `get_or_create` and reuse the existing record. **No duplicate processing.**
  </Accordion>
  <Accordion title="Why is jitter important?">
    Imagine 100 jobs fail at once due to a downstream blip. Without jitter, all 100 retry at exactly t+1s, then exactly t+3s, etc. — synchronized retry storms. With jitter, retries spread out and the downstream recovers smoothly.
  </Accordion>
  <Accordion title="`asyncio.wait_for(work(), timeout=...)`">
    Cancels `work()` if it doesn't finish in `timeout_s`. Critical for stuck jobs — a hung HTTP call would otherwise hold a worker slot forever.
  </Accordion>
  <Accordion title="Difference between `PermanentError` and a regular exception?">
    Regular exception → assumed transient → retry with backoff. `PermanentError` → "this will never succeed" → straight to DLQ. Use it for: malformed inputs, missing dependencies, business-rule violations.
  </Accordion>
</AccordionGroup>

## Quick check

<AccordionGroup>
  <Accordion title="What happens if the API restarts mid-job?">
    The in-memory `asyncio.Task` is killed. The `JobRecord` row stays in `running`. To handle this properly, add a startup sweep:
    ```python
    @asynccontextmanager
    async def lifespan(app):
        async with async_session() as db:
            await db.execute(
                update(JobRecord).where(JobRecord.status == "running").values(status="queued")
            )
            await db.commit()
        yield
    ```
    On the next eligible "queued" sweep (Module 28), they'll be re-attempted. With proper idempotency keys, this is safe.
  </Accordion>
  <Accordion title="What's the difference between cancellation and timeout?">
    Cancellation = explicit user action (or shutdown). Timeout = the work itself ran too long. Both raise `CancelledError`/`TimeoutError`; only timeout counts toward retry budget.
  </Accordion>
  <Accordion title="When should I write a job to the DB vs just `asyncio.create_task`?">
    DB-tracked: long-running, must survive restart, has retry semantics, has business meaning ("did this enrollment process run?"). In-memory: fire-and-forget side effects (analytics ping, log emit).
  </Accordion>
  <Accordion title="What about the 'thundering herd' on startup?">
    If you reset 1000 stuck `running` to `queued` on startup, they all start at once. Add a small random delay before each, or process in batches with concurrency caps.
  </Accordion>
</AccordionGroup>

## Insight

<Tip>
  **Idempotency keys are the secret weapon of reliable workers.** Once your worker can be safely re-run (with the same key) and produce the same result, every other concern simplifies: retries are safe, network blips become non-events, "did this job already run?" becomes a DB lookup. The whole DLQ + retry stack rests on this one property.
</Tip>

## Real-world reference

AnnotateHub's `BackgroundTaskRunner` doesn't have retry semantics — that's a real gap. Production systems with these requirements typically use Celery (Module 28) where the retry/DLQ machinery is built-in. This module shows what that machinery looks like under the hood.
