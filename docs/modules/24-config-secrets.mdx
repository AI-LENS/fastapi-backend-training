## Concept

The 12-factor app principle: **store config in the environment**.

```
Code  →  same in every environment
Config →  injected per environment (env vars)
```

Why: the same Docker image runs in dev, staging, and prod. The only thing that changes is config.

### Layers (later wins)

```
1. Class defaults (in code)        ← lowest priority
2. .env file
3. Process environment variables
4. Command-line overrides          ← highest priority
```

### Three categories of config

| Category | Example | Where it lives |
|---|---|---|
| **App config** | `LOG_LEVEL=INFO`, `API_PREFIX=/api/v1` | `.env` (committed: `.env.example`) |
| **Per-env config** | `DB_URL=postgres://...prod-host` | `.env.production` (NEVER committed) |
| **Secrets** | `SECRET_KEY`, `DB_PASSWORD`, API tokens | Secret manager (Vault, AWS Secrets Manager, 1Password) — NEVER in any `.env` file in git |

## Walkthrough

### Step 1 — Strict separation of files

```bash .env.example
# Committed to git. Documents every required variable. Empty/safe values only.

# App
ENROLLMENT_LOG_LEVEL=INFO
ENROLLMENT_API_PREFIX=/api/v1

# Database
ENROLLMENT_DB_URL=sqlite+aiosqlite:///./enrollment.db

# Auth — replace with a real secret in your local .env
ENROLLMENT_SECRET_KEY=please-change-me
ENROLLMENT_ACCESS_TOKEN_MINUTES=60
ENROLLMENT_REFRESH_TOKEN_DAYS=7

# Performance
ENROLLMENT_DEFAULT_LIST_LIMIT=50
ENROLLMENT_SLOW_REQUEST_MS=500

# CORS
ENROLLMENT_CORS_ORIGINS=["http://localhost:3000"]
```

```bash .env
# Local dev only. Never committed (.gitignored).
ENROLLMENT_LOG_LEVEL=DEBUG
ENROLLMENT_SECRET_KEY=local-dev-secret-replace-in-production
ENROLLMENT_DB_URL=sqlite+aiosqlite:///./enrollment.db
```

```bash .env.production.example
# Documents what production needs. Real values come from secret manager.
ENROLLMENT_LOG_LEVEL=INFO
ENROLLMENT_DB_URL=postgresql+asyncpg://USER:PASS@HOST/DB
ENROLLMENT_SECRET_KEY=  # injected from secret manager at deploy time
ENROLLMENT_CORS_ORIGINS=["https://app.example.com"]
```

### Step 2 — Make the secret_key strict

This is a partial diff — **add to your existing `app/config.py`**, don't replace the file. The `BaseSettings` and `SettingsConfigDict` imports from Module 04 stay.

```python app/config.py
# Add these imports alongside the existing ones from Module 04.
from pydantic import Field, field_validator


class Settings(BaseSettings):
    # ... existing fields stay ...

    secret_key: str = Field(..., min_length=32)
    """JWT signing key. Must be at least 32 chars; required."""

    @field_validator("secret_key")
    @classmethod
    def reject_dev_default(cls, v: str) -> str:
        if v in {"please-change-me", "change-me-in-production", "local-dev-secret-replace-in-production"}:
            # Allow in local dev (where ENROLLMENT_LOG_LEVEL=DEBUG)
            import os
            if os.environ.get("ENROLLMENT_LOG_LEVEL", "").upper() != "DEBUG":
                raise ValueError(
                    "ENROLLMENT_SECRET_KEY appears to be a dev placeholder. "
                    "Set a real secret (e.g., `openssl rand -hex 32`)."
                )
        return v
```

If someone tries to deploy with the placeholder, the app **refuses to start**. Fail fast > fail in prod.

### Step 3 — Per-environment file selection

Replace the `model_config = SettingsConfigDict(...)` you wrote in Module 04 with the version below — that's the only change to the class declaration; every other field/validator stays.

```python app/config.py
# Add `import os` near the top of the file if it isn't already imported.
import os


_env = os.environ.get("ENROLLMENT_ENV", "development")


class Settings(BaseSettings):
    model_config = SettingsConfigDict(
        env_file=(
            f".env.{_env}",   # e.g., .env.production — checked first
            ".env",            # fallback
        ),
        env_file_encoding="utf-8",
        env_prefix="ENROLLMENT_",
        case_sensitive=False,
    )
    # ... existing fields & validators stay ...
```

Now `ENROLLMENT_ENV=production uvicorn ...` loads `.env.production` first, falling back to `.env`. In containers, you typically skip `.env` files entirely and rely on real env vars.

### Step 4 — Generating secrets

```bash
# Generate a secure secret key
openssl rand -hex 32
# 8c4c5f...64-char hex string
```

Use this for `ENROLLMENT_SECRET_KEY`. **Different per environment.** A leaked dev secret should not affect production.

### Step 5 — Documenting secrets without leaking them

```bash secrets/README.md
# Required secrets

| Name                          | Purpose                       | Where it comes from         |
|-------------------------------|-------------------------------|-----------------------------|
| ENROLLMENT_SECRET_KEY         | JWT signing key                | secret manager → env var    |
| ENROLLMENT_DB_URL             | Postgres connection            | secret manager → env var    |
| OPENROUTER_API_KEY (future)   | LLM API access                 | secret manager → env var    |

Never commit a real secret. To set up a new env:
1. Generate values: `openssl rand -hex 32` for keys; secret manager for credentials
2. Inject as env vars in your deploy platform (Docker, k8s, etc.)
3. Verify on first start — app should refuse with the dev placeholder values
```

### What's new

<AccordionGroup>
  <Accordion title="Why `.env.example` and not just one `.env`?">
    `.env.example` is committed and shows new contributors *what* env vars to set. `.env` is local and never committed (would leak secrets). Same idea applies to `.env.production.example`.
  </Accordion>
  <Accordion title="What's `pydantic-settings` doing differently from os.environ?">
    Type validation, defaults, structured layering, and fail-fast on missing required values. Plain `os.environ.get(...)` returns None silently and you find out at runtime.
  </Accordion>
  <Accordion title="What about Doppler / 1Password / Vault?">
    They're secret managers — they inject secrets into your environment at runtime. Your code still reads from `os.environ`. The "interface" is the same; only how secrets *got there* differs. For local dev: `direnv` + 1Password CLI is a popular combo.
  </Accordion>
  <Accordion title="`field_validator` — what's that?">
    Pydantic v2 way to validate a field beyond its type. Runs at instance creation. Raise to fail; return to set the validated value.
  </Accordion>
</AccordionGroup>

## Try it

<Steps>
  <Step title="Try to start the app with a placeholder secret">
    Edit `.env` to `ENROLLMENT_SECRET_KEY=please-change-me`, set `ENROLLMENT_LOG_LEVEL=INFO`, restart. App refuses to start with a clear validation error.
  </Step>
  <Step title="Generate and use a real secret">
    ```bash
    SECRET=$(openssl rand -hex 32)
    echo "ENROLLMENT_SECRET_KEY=$SECRET" >> .env
    ```
    Restart. App starts.
  </Step>
  <Step title="Verify per-env loading">
    ```bash
    ENROLLMENT_ENV=production uvicorn app.main:app
    ```
    If you don't have `.env.production`, it falls back to `.env`. Either way, it logs the env on startup (you may want to add this).
  </Step>
</Steps>

## Quick check

<AccordionGroup>
  <Accordion title="Should secrets ever be in source control?">
    Never. Even private repos: a single misconfigured fork later, and secrets are public. Secret managers are the only safe place.
  </Accordion>
  <Accordion title="What about secrets in Docker images?">
    Don't bake them in. Use ENV at run-time (`docker run -e SECRET=...`) or mounted secrets files (Kubernetes Secrets, Docker Swarm secrets).
  </Accordion>
  <Accordion title="What if I leak a secret?">
    **Rotate immediately.** Issue a new secret. Invalidate the old one (in JWT's case, this means all existing tokens become invalid). Audit logs to see if the leak was used. Document in a postmortem.
  </Accordion>
  <Accordion title="My CI fails because it can't read .env">
    Right — CI doesn't get your local `.env`. Set CI env vars in the CI provider's UI (GitHub secrets, GitLab variables, etc.). Module 26b shows this.
  </Accordion>
</AccordionGroup>

## Insight

<Tip>
  **Treat config like code reviews: every change to a default, every new env var, gets reviewed.** Misconfigured production is a top cause of incidents — and the misconfiguration is almost always a default someone added without thinking. `.env.example` is a contract: every entry there is a deliberate decision.
</Tip>
